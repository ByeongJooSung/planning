## 1. 개요

### 1.1 배경
서비스 기획 업무는 요구사항을 받아 **기획안 → 정보구조도(IA) → 다이어그램 → 스토리보드 → 프로토타입** 순서로 산출물을 만든다. 현재는 단계마다 문서를 수작업으로 만들고, 요구사항이 추가·변경되면 앞 단계부터 모든 산출물을 사람이 직접 찾아 고쳐야 한다. 그 결과 다음 문제가 반복된다.

- 기획안을 쓰기 위한 정보가 부족한 채 작성이 시작되고, 뒤 단계에서 되묻는 일이 생긴다.
- 기존 운영 서비스의 구조(메뉴, 화면, 정책)를 고려하지 않은 기획이 나온다.
- 산출물 사이의 연결(요구사항 ↔ 화면 ↔ 플로우)이 끊겨서 **요구사항 누락**이 생긴다.
- 변경 요청이 오면 무엇이 바뀌었는지(As-Is / To-Be)를 설명하는 자료를 따로 만들어야 한다.
- 공공기관 제출용처럼 정해진 양식(PPT 장표형, 페이지 연속 표기)에 맞추는 데 시간이 많이 든다.

### 1.2 목적
어떤 서비스든 **프로젝트 단위**로 만들어서, 5단계 기획 산출물을 **구조화된 단계(Stage)** 에 따라 생성·관리하는 프로그램을 만든다.

1. 단계마다 작업자에게 **필요한 정보를 질문하고**, 충분히 모였을 때만 산출물을 생성한다.
2. **신규 구축**인지 **기존 운영 서비스 개선**인지에 따라 다른 경로로 동작한다(기존 서비스는 시스템 분석을 먼저 한다).
3. 모든 산출물을 **하나의 기획 데이터 모델(Single Source of Truth)** 에서 만들어, 요구사항부터 프로토타입까지 추적할 수 있게 한다. 추적 결과는 프로젝트별 **요구사항 추적표(RTM)** 로 계속 관리한다.
4. 한 프로젝트 안의 **시스템 구분**(예: 대국민 포털, 민원포털, 심사자·관리자 시스템)을 나누어 관리하고, 하나의 요구사항을 시스템별 **Task** 로 나누어 각 산출물에 반영한다.
5. 추가 요구사항(메일, 텍스트, 파일)이 들어오면 **앞 단계부터 차례로 반영**하고, **변경 전/후를 시각화**한다.
6. PPT, Figma, PDF, HTML 등 실무 도구로 **내보내기(Export)** 를 지원한다.

### 1.3 성공 지표 (KPI)
| 지표 | 목표 |
|---|---|
| 요구사항 → 스토리보드 추적 커버리지 | 100% (미매핑 요구사항 0건일 때만 산출물 "완료" 처리 가능) |
| 시스템별 Task → 화면 매핑률 | 100% (화면이 없는 Task는 "화면 없음(배치·자동 처리)" 사유 필수) |
| RTM 최신화 | 산출물·CR 반영 즉시 자동 갱신, 수동 정리 작업 0건 |
| 기획안~스토리보드 초안 작성 시간 | 기존 수작업 대비 50% 이상 단축 |
| 변경 요청 반영 시 영향 산출물 자동 식별률 | 90% 이상 |
| 공공기관 양식 스토리보드 재편집 필요 페이지 | 전체의 10% 이하 |
| 단계별 "정보 부족" 상태로 생성된 산출물 | 0건 (게이트 통과 필수) |

### 1.4 범위
**포함 (In Scope)**
- 프로젝트 생성·관리, 단계별 파이프라인(S0~S5), 변경 요청(CR) 처리
- 프로젝트 내 시스템 구분 관리, 요구사항의 시스템별 Task 분해
- 프로젝트별 요구사항 추적표(RTM) 관리·내보내기
- 인터뷰형 정보 수집, 자료 업로드·분석
- 기존 서비스 분석(기존 IA 문서, 웹페이지 전수조사, 소스코드 전수조사)
- 산출물 생성, 버전 관리, As-Is / To-Be 비교 시각화
- Export: PPTX, PDF, Figma, SVG/PNG, Mermaid, draw.io, XLSX, HTML

**제외 (Out of Scope)**
- 개발자 관점 설계 산출물(API 명세, DB 설계, 시퀀스 다이어그램 등)
- 실제 서비스 개발 및 배포
- UI 비주얼 디자인 시안(프로토타입은 와이어프레임 수준 기본, 디자인 시스템 연동은 선택 사항)

## 2. 사용자 및 사용 시나리오

### 2.1 사용자 (Persona)
| 구분 | 설명 | 주요 니즈 |
|---|---|---|
| 기획자 (주 사용자) | 요구사항을 받아 산출물을 만드는 사람 | 빠른 초안, 누락 방지, 양식 준수, 변경 대응 |
| PM / PL | 프로젝트 전체를 관리하는 사람 | 단계별 진행 현황, 변경 이력, 요구사항 충족 여부 |
| 검토자 (고객사, 발주처) | 산출물을 검토·승인하는 사람 | 읽기 쉬운 문서, 변경점이 명확한 자료 |
| 디자이너 | 스토리보드와 프로토타입을 이어받는 사람 | Figma로 내보내기, 화면 ID 체계 |

### 2.2 대표 시나리오
**A. 신규 프로젝트**
1. 프로젝트 생성 → 유형 "신규 구축" 선택 → 요구사항 원문(RFP, 메일 등) 업로드
2. 인터뷰로 기획안에 필요한 정보 수집 → 충분성 게이트 통과 → 기획안 생성
3. 기획안 기준으로 IA를 새로 설계(화면 ID 자동 부여)
4. 프로세스 플로우와 사용자 플로우 생성 → PPT/Figma로 내보내기
5. 스토리보드 생성(일반형 또는 공공기관 제출형) → 프로토타입 생성

**B. 기존 운영 서비스 개선**
1. 프로젝트 생성 → 유형 "기존 서비스" 선택 → 변경 범위 선택(신규 메뉴 추가 / 기존 메뉴 수정)
2. 시스템 분석: 기존 IA를 요청하고, 없으면 웹 전수조사 또는 소스 전수조사 자료를 요청
3. 분석 결과를 반영해서 기존 구조에 맞는 기획안 생성
4. IA: 기존 IA를 참조해서 보완·수정(변경 표시). 기존 메뉴 수정만 하는 경우 IA 단계는 **패스**
5. 기존 다이어그램이 있으면 수정 반영하고 As-Is / To-Be 비교 자료 생성
6. 스토리보드, 프로토타입 생성

**C. 추가 요구사항 반영**
1. 메일 본문, 텍스트, 파일로 추가 요구사항 입력
2. 요구사항을 분해·분류하고, 영향받는 단계와 산출물 식별
3. 앞 단계(기획안)부터 차례로 반영안 생성 → 작업자가 단계별로 승인
4. 변경 전/후 비교 시각화와 변경 설명서 생성, 버전 증가

**D. 여러 시스템에 걸친 요구사항 (예: 대국민 정보공개)**
1. 프로젝트 생성 시 시스템 구분 등록: 대국민 포털(PUB), 민원포털(CVL), 심사자·관리자 시스템(ADM)
2. 요구사항 `REQ-012 대국민 정보공개` 입력 → 도구가 시스템별 Task로 분해안을 제시
   - `REQ-012-T01` [민원포털] 민원인이 자료를 등록하고 공개 신청
   - `REQ-012-T02` [심사자] 심사자가 검토 후 승인(또는 반려·보완 요청)
   - `REQ-012-T03` [대국민] 승인된 자료를 대국민 목록·상세에 공개
3. 작업자가 분해안을 확인·수정(Task 추가/삭제, 시스템 변경, 순서 지정)
4. 각 Task가 해당 시스템의 IA 화면, 플로우 레인, 스토리보드 화면에 연결되고, RTM에서 요구사항 × 시스템 매트릭스로 충족 여부를 확인

## 3. 핵심 개념

### 3.1 프로젝트 유형과 변경 범위
| 구분 | 값 | 설명 |
|---|---|---|
| 서비스 유형 | `NEW` 신규 구축 | 참조할 기존 시스템이 없음 |
| | `EXISTING` 기존 운영 서비스 | 시스템 분석(S0-A)이 필수 |
| 변경 범위 (EXISTING일 때) | `NEW_MENU` 신규 메뉴·기능 추가 | IA 보완 필요 |
| | `MODIFY` 기존 메뉴 수정·기존 메뉴에 기능 적용 | IA 단계 패스 가능 |
| | `RENEWAL` 전면 개편 | IA 재설계, 기존 IA는 As-Is로 사용 |

### 3.2 단계(Stage) 파이프라인
```
S0 프로젝트 설정·자료 수집
 └ S0-A 기존 서비스 분석 (EXISTING일 때만)
S1 기획안
S2 정보구조도(IA)          ← MODIFY이면 패스(영향 화면 ID만 등록)
S3 다이어그램 (프로세스 플로우 + 사용자 플로우)
S4 스토리보드(화면설계서)
S5 프로토타입
CR 변경 요청 (모든 단계에 걸쳐 동작)
```
각 단계는 다음 상태를 가진다.

`미시작 → 정보수집중 → 게이트 통과 → 생성됨(초안) → 검토중 → 확정` (+ `패스`, `변경 필요`)

- **게이트(Gate)**: 단계별 필수 정보 체크리스트. 필수 항목이 모두 채워져야 생성할 수 있다. 작업자가 "가정으로 진행"을 고르면 해당 항목은 **가정(Assumption)** 으로 기록되고, 산출물에 가정 사항으로 표시된다.
- **상위 단계가 바뀌면** 하위 단계는 자동으로 `변경 필요` 상태가 된다.

### 3.3 기획 데이터 모델 (Single Source of Truth)
모든 산출물은 아래 모델에서 렌더링된다. 문서를 직접 고치면 모델에 역반영된다(양방향). 역반영이 안 되는 자유 편집 영역은 "수동 편집 영역"으로 따로 표시한다.

```
Project
 ├─ System[]            시스템 구분 (대국민 PUB, 민원포털 CVL, 심사자·관리자 ADM …)
 ├─ Source[]            업로드 원문 (RFP, 메일, 파일, URL, 소스 저장소)
 ├─ Requirement[]       REQ-001 … (출처, 유형, 우선순위, 상태)
 │   └─ Task[]          REQ-001-T01 … (시스템 구분, 행위자, 처리 내용, 선후행, 상태)
 ├─ RTM                 요구사항 추적표 (모델에서 자동 계산 + 수동 비고·확인 이력)
 ├─ Assumption[] / OpenIssue[]
 ├─ AnalysisResult      기존 서비스 분석 결과 (As-Is IA, 화면 목록, 정책)
 ├─ PlanDoc             기획안 섹션
 ├─ IANode[]            시스템별 메뉴 트리, 화면 ID, 화면 유형(페이지/팝업/레이어)
 ├─ Flow[]              PROCESS / USER 플로우, 노드·엣지
 ├─ Screen[]            스토리보드 화면 (IA 화면 ID와 1:1 또는 1:N)
 │   └─ Component[]     UI 요소, 옵션 값, 유효성 규칙, 디스크립션
 ├─ Prototype           화면, 핫스팟, 상태 전이
 ├─ ChangeRequest[]     CR-001 …
 └─ Version[]           단계별 스냅샷 (v1.0, v1.1 …)
```

### 3.4 추적성(Traceability)과 요구사항 추적표(RTM)
`REQ-xxx → 시스템별 Task(REQ-xxx-Tnn) → 기획안 섹션 → IA 화면 ID → 플로우 노드 → 스토리보드 화면/디스크립션 번호 → 프로토타입 화면`

- 추적의 기본 단위는 **Task** 이다. 요구사항은 소속 Task가 모두 충족되어야 "충족"이 된다.
- RTM은 프로젝트마다 **하나의 살아 있는 산출물**로 관리한다. 산출물 생성·수정·CR 반영 때마다 자동으로 갱신되고, 버전별 스냅샷이 남는다.
- 매핑되지 않은 요구사항·Task가 있으면 해당 단계를 **확정할 수 없다**(사유를 적고 "제외 승인"한 경우는 예외).
- 요구사항을 반드시 충족하기 위한 핵심 장치이다.

### 3.5 시스템 구분과 Task
한 프로젝트에는 사용자와 화면이 다른 여러 시스템이 함께 있을 수 있다(특히 공공 사업).

| 시스템 구분 (예시) | 코드 | 주 사용자 | 설명 |
|---|---|---|---|
| 대국민 포털 | PUB | 일반 국민(비회원 포함) | 공개 정보 조회, 안내 |
| 민원포털 | CVL | 민원인(회원) | 신청, 자료 등록, 처리 현황 조회 |
| 심사자·관리자 시스템 | ADM | 심사자, 운영 관리자 | 검토, 승인·반려, 운영 관리 |
| 외부 연계 | EXT | 외부 기관·시스템 | 화면 없음, 프로세스 플로우 레인으로만 표시 |

- 시스템 구분은 프로젝트마다 자유롭게 정의한다(이름, 코드, 주 사용자·권한, 채널, 화면 ID 접두어, 색상).
- **요구사항 하나가 여러 시스템에 걸치면 시스템별 Task로 나눈다.** 예: `REQ-012 대국민 정보공개`
  ```
  [CVL 민원포털] 민원인 자료 등록·공개 신청
        ↓
  [ADM 심사자]   검토 → 승인 / 반려·보완 요청(→ 민원포털로 되돌아감)
        ↓ 승인
  [PUB 대국민]   공개 목록·상세에 반영
  ```
- Task는 **시스템 구분, 행위자, 처리 내용, 입력·출력(예: 자료 상태 "공개 신청 → 승인 → 공개"), 선행 Task** 를 가진다. 선후행 관계는 프로세스 플로우의 뼈대가 된다.
- 여러 Task에 걸쳐 쓰이는 **상태값**(예: 등록 → 공개신청 → 심사중 → 승인/반려 → 공개)은 기획안의 정책 정의에 한 번 정의하고, 모든 시스템의 스토리보드가 같은 값을 참조한다.
- 산출물은 시스템 구분별로 보기·내보내기를 할 수 있고, 전체 통합 보기도 제공한다.

### 3.6 작업 단위(Task)와 통합 산출물
```
요구사항 등록 ─┬─ Task 자동 생성 ─┐
               └─ Task 수동 생성 ─┤
                                   ▼
             Task 상세: 프로세스 플로우 · 화면설계서 · 프로토타입   (Task 단위로 작성)
                                   ▼  설계완료
     통합 산출물: 정보구조도 · 요구사항 추적표 · 시스템별 프로세스 플로우   (프로젝트 단위로 통합)
```
- 산출물은 Task 단위로 만들고, 모델이 하나이므로 통합 산출물은 따로 편집하지 않아도 자동으로 합쳐진다.
- 통합 산출물에는 각 화면·노드의 Task 진행 상태를 함께 표시해, 아직 작업 중인 부분이 드러나게 한다.
- 시스템별 프로세스 플로우: 전체 통합 플로우에서 한 시스템 레인만 남기고, 다른 시스템으로 넘어가는 지점은 연결 노드로 표시한다.

### 4.3 S0-A — 기존 서비스 분석 (F-ANL) — EXISTING 전용
분석 입력은 아래 우선순위대로 요청한다. 앞의 것이 없을 때 다음 방법을 요청한다.

| 순위 | 입력 | 처리 |

```
  → 검사(형식·디자인 시스템 컴포넌트·폐기 ID·연결 누락) → 적용 / 적용 해제
```

### 4.10C 디자인 시스템 섹션별 조정 · 댓글 수정 (F-DSR)
디자인 시스템은 한 번에 통째로 고치기보다 **보고 있는 부분을 콕 집어** 고친다.

| 조정 방법 | 쓰는 곳 | 바꿀 수 있는 범위 |
|---|---|---|
| 섹션별 프롬프트 | 색상 / 글꼴 / 간격·그리드 / 모서리·그림자 / 컨트롤 / 레이아웃 규칙 / 화면 템플릿 / 컴포넌트마다 | 그 섹션의 값만 (예: 색상 → `tokens.color`, 컴포넌트 → 그 컴포넌트의 스타일 변수) |
| 이미지 댓글 | 화면 템플릿·컴포넌트 이미지를 누르면 실제 규격 검토 화면이 열리고, 누른 자리에 번호 핀을 꽂아 댓글을 남긴다. “컴포넌트 번호 보기”로 요소마다 번호 라벨을 띄워 번호를 눌러 댓글을 달 수도 있다 | 핀이 가리키는 컴포넌트·위치·문구를 근거로 수정 패치 생성 |
| 전역 프롬프트 | 디자인 시스템 맨 위 | 새 컴포넌트 추가, 여러 섹션에 걸친 변경 |

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-DSR-01 | 섹션별 미세조정 | 섹션 머리의 “이 섹션 조정”에서 프롬프트 입력 → 그 섹션 범위의 패치만 생성·검사(범위 밖 값은 적용 불가) → 미리보기 → 적용 | P0 |

| F-DSR-03 | 이미지 핀 댓글 | 템플릿·컴포넌트 이미지 클릭 → 실제 규격 검토 레이어 → 누른 자리에 번호 핀 + 댓글. 핀은 아래 요소(컴포넌트 ID, 문구)를 자동 기록 | P0 |
| F-DSR-04 | 번호 라벨 | 검토 레이어에서 컴포넌트마다 번호 라벨 표시, 라벨을 눌러 그 컴포넌트에 댓글 | P0 |
| F-DSR-05 | 댓글로 수정 요청 | 열린 댓글을 모아 수정 패치 생성 → 적용하면 반영한 댓글은 “반영됨(rN)”으로 닫힘. 댓글은 페이지를 보는 모두와 공유 | P0 |
| F-DSR-06 | 누적 적용·되돌리기 | 섹션·댓글·전역 조정이 적용될 때마다 개정 번호가 오르고 누적된다. 개정 이력(범위·요청·바뀐 값), 마지막 적용 되돌리기 | P0 |
| F-DSR-07 | 전역 프롬프트 | 새 컴포넌트 생성(ID·이름·분류·설명·변형 + 스타일 변수)과 섹션을 넘나드는 변경 | P0 |

```
[Web UI]  프로젝트 대시보드 · 인터뷰 · 단계별 편집기 · Diff 뷰어
    │
[API 서버]

    ├─ Traceability / RTM           (시스템별 Task 분해, 추적성, 커버리지 검사, 추적표 관리)

    └─ Renderer / Exporter          (PPTX, PDF, DOCX, XLSX, SVG, Figma, HTML)
    │
[저장소]  프로젝트 DB(JSON 문서 모델) + 파일 저장소(원문, 캡처, 산출물)
```

**권장 기술 (확정 전)**
- 프론트엔드: React + TypeScript, 다이어그램 편집은 React Flow + ELK 자동 정렬
- 백엔드: Node.js(TypeScript), 크롤러는 Playwright
- LLM: Claude API (구조화 출력으로 데이터 모델 JSON 생성)
- Export: pptxgenjs(PPTX), docx(DOCX), exceljs(XLSX), Playwright PDF 출력, Figma Plugin API 또는 Figma MCP
- 저장: 파일 기반 프로젝트 폴더(초기) → PostgreSQL(다중 사용자 단계)

**프로젝트 폴더 구조 (파일 기반 저장 시)**
