## 1. 개요

### 1.1 배경
서비스 기획 업무는 요구사항을 받아 **기획안 → 정보구조도(IA) → 다이어그램 → 스토리보드 → 프로토타입** 순서로 산출물을 만든다. 현재는 단계마다 문서를 수작업으로 만들고, 요구사항이 추가·변경되면 앞 단계부터 모든 산출물을 사람이 직접 찾아 고쳐야 한다. 그 결과 다음 문제가 반복된다.

- 기획안을 쓰기 위한 정보가 부족한 채 작성이 시작되고, 뒤 단계에서 되묻는 일이 생긴다.
- 기존 운영 서비스의 구조(메뉴, 화면, 정책)를 고려하지 않은 기획이 나온다.
- 산출물 사이의 연결(요구사항 ↔ 화면 ↔ 플로우)이 끊겨서 **요구사항 누락**이 생긴다.
- 변경 요청이 오면 무엇이 바뀌었는지(As-Is / To-Be)를 설명하는 자료를 따로 만들어야 한다.
- 공공기관 제출용처럼 정해진 양식(PPT 장표형, 페이지 연속 표기)에 맞추는 데 시간이 많이 든다.

### 1.2 목적
어떤 서비스든 **프로젝트 단위**로 만들어서, 5단계 기획 산출물을 **구조화된 단계(Stage)** 에 따라 생성·관리하는 프로그램을 만든다.

1. 단계마다 작업자에게 **필요한 정보를 질문하고**, 충분히 모였을 때만 산출물을 생성한다.
2. **신규 구축**인지 **기존 운영 서비스 개선**인지에 따라 다른 경로로 동작한다(기존 서비스는 시스템 분석을 먼저 한다).
3. 모든 산출물을 **하나의 기획 데이터 모델(Single Source of Truth)** 에서 만들어, 요구사항부터 프로토타입까지 추적할 수 있게 한다.
4. 추가 요구사항(메일, 텍스트, 파일)이 들어오면 **앞 단계부터 차례로 반영**하고, **변경 전/후를 시각화**한다.
5. PPT, Figma, PDF, HTML 등 실무 도구로 **내보내기(Export)** 를 지원한다.

### 1.3 성공 지표 (KPI)
| 지표 | 목표 |
|---|---|
| 요구사항 → 스토리보드 추적 커버리지 | 100% (미매핑 요구사항 0건일 때만 산출물 "완료" 처리 가능) |
| 기획안~스토리보드 초안 작성 시간 | 기존 수작업 대비 50% 이상 단축 |
| 변경 요청 반영 시 영향 산출물 자동 식별률 | 90% 이상 |
| 공공기관 양식 스토리보드 재편집 필요 페이지 | 전체의 10% 이하 |
| 단계별 "정보 부족" 상태로 생성된 산출물 | 0건 (게이트 통과 필수) |

### 1.4 범위
**포함 (In Scope)**
- 프로젝트 생성·관리, 단계별 파이프라인(S0~S5), 변경 요청(CR) 처리
- 인터뷰형 정보 수집, 자료 업로드·분석
- 기존 서비스 분석(기존 IA 문서, 웹페이지 전수조사, 소스코드 전수조사)
- 산출물 생성, 버전 관리, As-Is / To-Be 비교 시각화
- Export: PPTX, PDF, Figma, SVG/PNG, Mermaid, draw.io, XLSX, HTML

**제외 (Out of Scope)**
- 개발자 관점 설계 산출물(API 명세, DB 설계, 시퀀스 다이어그램 등)
- 실제 서비스 개발 및 배포
- UI 비주얼 디자인 시안(프로토타입은 와이어프레임 수준 기본, 디자인 시스템 연동은 선택 사항)

## 2. 사용자 및 사용 시나리오

### 2.1 사용자 (Persona)
| 구분 | 설명 | 주요 니즈 |
|---|---|---|
| 기획자 (주 사용자) | 요구사항을 받아 산출물을 만드는 사람 | 빠른 초안, 누락 방지, 양식 준수, 변경 대응 |
| PM / PL | 프로젝트 전체를 관리하는 사람 | 단계별 진행 현황, 변경 이력, 요구사항 충족 여부 |
| 검토자 (고객사, 발주처) | 산출물을 검토·승인하는 사람 | 읽기 쉬운 문서, 변경점이 명확한 자료 |
| 디자이너 | 스토리보드와 프로토타입을 이어받는 사람 | Figma로 내보내기, 화면 ID 체계 |

### 2.2 대표 시나리오
**A. 신규 프로젝트**
1. 프로젝트 생성 → 유형 "신규 구축" 선택 → 요구사항 원문(RFP, 메일 등) 업로드
2. 인터뷰로 기획안에 필요한 정보 수집 → 충분성 게이트 통과 → 기획안 생성
3. 기획안 기준으로 IA를 새로 설계(화면 ID 자동 부여)
4. 프로세스 플로우와 사용자 플로우 생성 → PPT/Figma로 내보내기
5. 스토리보드 생성(일반형 또는 공공기관 제출형) → 프로토타입 생성

**B. 기존 운영 서비스 개선**
1. 프로젝트 생성 → 유형 "기존 서비스" 선택 → 변경 범위 선택(신규 메뉴 추가 / 기존 메뉴 수정)
2. 시스템 분석: 기존 IA를 요청하고, 없으면 웹 전수조사 또는 소스 전수조사 자료를 요청
3. 분석 결과를 반영해서 기존 구조에 맞는 기획안 생성
4. IA: 기존 IA를 참조해서 보완·수정(변경 표시). 기존 메뉴 수정만 하는 경우 IA 단계는 **패스**
5. 기존 다이어그램이 있으면 수정 반영하고 As-Is / To-Be 비교 자료 생성
6. 스토리보드, 프로토타입 생성

**C. 추가 요구사항 반영**
1. 메일 본문, 텍스트, 파일로 추가 요구사항 입력
2. 요구사항을 분해·분류하고, 영향받는 단계와 산출물 식별
3. 앞 단계(기획안)부터 차례로 반영안 생성 → 작업자가 단계별로 승인
4. 변경 전/후 비교 시각화와 변경 설명서 생성, 버전 증가

## 3. 핵심 개념

### 3.1 프로젝트 유형과 변경 범위
| 구분 | 값 | 설명 |
|---|---|---|
| 서비스 유형 | `NEW` 신규 구축 | 참조할 기존 시스템이 없음 |
| | `EXISTING` 기존 운영 서비스 | 시스템 분석(S0-A)이 필수 |
| 변경 범위 (EXISTING일 때) | `NEW_MENU` 신규 메뉴·기능 추가 | IA 보완 필요 |
| | `MODIFY` 기존 메뉴 수정·기존 메뉴에 기능 적용 | IA 단계 패스 가능 |
| | `RENEWAL` 전면 개편 | IA 재설계, 기존 IA는 As-Is로 사용 |

### 3.2 단계(Stage) 파이프라인
```
S0 프로젝트 설정·자료 수집
 └ S0-A 기존 서비스 분석 (EXISTING일 때만)
S1 기획안
S2 정보구조도(IA)          ← MODIFY이면 패스(영향 화면 ID만 등록)
S3 다이어그램 (프로세스 플로우 + 사용자 플로우)
S4 스토리보드(화면설계서)
S5 프로토타입
CR 변경 요청 (모든 단계에 걸쳐 동작)
```
각 단계는 다음 상태를 가진다.

`미시작 → 정보수집중 → 게이트 통과 → 생성됨(초안) → 검토중 → 확정` (+ `패스`, `변경 필요`)

- **게이트(Gate)**: 단계별 필수 정보 체크리스트. 필수 항목이 모두 채워져야 생성할 수 있다. 작업자가 "가정으로 진행"을 고르면 해당 항목은 **가정(Assumption)** 으로 기록되고, 산출물에 가정 사항으로 표시된다.
- **상위 단계가 바뀌면** 하위 단계는 자동으로 `변경 필요` 상태가 된다.

### 3.3 기획 데이터 모델 (Single Source of Truth)
모든 산출물은 아래 모델에서 렌더링된다. 문서를 직접 고치면 모델에 역반영된다(양방향). 역반영이 안 되는 자유 편집 영역은 "수동 편집 영역"으로 따로 표시한다.

```
Project
 ├─ Source[]            업로드 원문 (RFP, 메일, 파일, URL, 소스 저장소)
 ├─ Requirement[]       REQ-001 … (출처, 유형, 우선순위, 상태)
 ├─ Assumption[] / OpenIssue[]
 ├─ AnalysisResult      기존 서비스 분석 결과 (As-Is IA, 화면 목록, 정책)
 ├─ PlanDoc             기획안 섹션
 ├─ IANode[]            메뉴 트리, 화면 ID, 화면 유형(페이지/팝업/레이어)
 ├─ Flow[]              PROCESS / USER 플로우, 노드·엣지
 ├─ Screen[]            스토리보드 화면 (IA 화면 ID와 1:1 또는 1:N)
 │   └─ Component[]     UI 요소, 옵션 값, 유효성 규칙, 디스크립션
 ├─ Prototype           화면, 핫스팟, 상태 전이
 ├─ ChangeRequest[]     CR-001 …
 └─ Version[]           단계별 스냅샷 (v1.0, v1.1 …)
```

### 3.4 추적성(Traceability)
`REQ-xxx → 기획안 섹션 → IA 화면 ID → 플로우 노드 → 스토리보드 화면/디스크립션 번호 → 프로토타입 화면`

- 모든 단계에서 **요구사항 추적 매트릭스(RTM)** 를 자동 생성한다.
- 매핑되지 않은 요구사항이 있으면 해당 단계를 **확정할 수 없다**(사유를 적고 "제외 승인"한 경우는 예외).
- 요구사항을 반드시 충족하기 위한 핵심 장치이다.

## 4. 기능 요구사항

> 우선순위: **P0** 필수(MVP) / **P1** 중요 / **P2** 선택

### 4.1 공통 — 프로젝트 관리 (F-PRJ)
| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-PRJ-01 | 프로젝트 생성 | 이름, 서비스 코드(화면 ID 접두어), 서비스 유형, 변경 범위, 대상 채널(PC/모바일/앱), 제출 양식(일반/공공기관) | P0 |
| F-PRJ-02 | 프로젝트 대시보드 | 단계별 상태, 게이트 충족률, RTM 커버리지, 열린 CR, 최근 변경 | P0 |
| F-PRJ-03 | 자료함 | 파일(PDF, DOCX, PPTX, XLSX, HWP, 이미지, EML), 텍스트, URL, Git 저장소 등록. 원문 보관, 텍스트 추출 | P0 |
| F-PRJ-04 | 버전 관리 | 단계별 스냅샷, 버전 번호, 비교, 되돌리기 | P0 |
| F-PRJ-05 | 프로젝트 템플릿 | 조직별 기본 설정(화면 ID 규칙, 스토리보드 양식, 질문 세트) 저장·재사용 | P1 |
| F-PRJ-06 | 권한·공유 | 소유자/편집자/검토자, 검토 코멘트 | P2 |

### 4.2 S0 — 요구사항 수집 및 인터뷰 (F-INT)
| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-INT-01 | 요구사항 추출 | 업로드된 원문에서 요구사항을 문장 단위로 뽑아 REQ-ID 부여, 출처(파일·페이지·문단) 연결 | P0 |
| F-INT-02 | 요구사항 분류 | 기능/비기능/정책/콘텐츠/제약, 우선순위(Must/Should/Could), 모호성 표시 | P0 |
| F-INT-03 | 인터뷰 엔진 | 단계별 질문 세트(부록 A)를 바탕으로 **아직 답이 없는 항목만** 질문. 답변은 해당 모델 필드에 바로 저장 | P0 |
| F-INT-04 | 후속 질문 | 답변이 모호하거나 서로 충돌하면 추가로 질문(예: "회원 전용"과 "비회원 주문 가능"이 충돌) | P0 |
| F-INT-05 | 충분성 게이트 | 필수 항목 충족률 표시. 미충족 항목은 "질문하기 / 자료 요청 / 가정으로 진행" 중 선택 | P0 |
| F-INT-06 | 자료 요청서 생성 | 부족한 자료를 고객·담당자에게 요청하는 메일·문서 초안 생성(요청 항목, 형식 예시, 기한) | P1 |
| F-INT-07 | 오픈 이슈 관리 | 미결 사항 목록, 담당자, 기한, 해결 시 자동 반영 | P1 |

### 4.3 S0-A — 기존 서비스 분석 (F-ANL) — EXISTING 전용
분석 입력은 아래 우선순위대로 요청한다. 앞의 것이 없을 때 다음 방법을 요청한다.

| 순위 | 입력 | 처리 |
|---|---|---|
| 1 | 기존 IA 문서(XLSX, PPT, 이미지) | 파싱해서 As-Is IA 트리 생성 |
| 2 | 기존 스토리보드·기획서 | 화면 목록, 정책, 용어 추출 |
| 3 | **웹페이지 전수조사** (URL + 필요 시 테스트 계정) | 크롤링으로 메뉴 트리, URL 목록, 페이지 제목, 화면 캡처 수집 |
| 4 | **소스 전수조사** (Git 저장소 또는 압축 파일) | 라우트·메뉴 정의·화면 컴포넌트를 추출해 화면 목록 생성 |
| 5 | 수동 입력 | 메뉴 트리 편집기로 직접 입력 |

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-ANL-01 | 분석 경로 판정 | 서비스 유형과 변경 범위에 따라 필요한 분석을 판정. `MODIFY`이면 **대상 메뉴 범위만** 분석 요청(전수조사 생략 가능) | P0 |

## 6. 시스템 구성 (제안)

```
[Web UI]  프로젝트 대시보드 · 인터뷰 · 단계별 편집기 · Diff 뷰어
    │
[API 서버]
    ├─ Project / Version 서비스      (스냅샷, 비교)
    ├─ Interview 엔진               (질문 세트, 게이트, 후속 질문)
    ├─ Generator (LLM 연동)         (기획안·IA·플로우·스토리보드 초안 생성)
    ├─ Analyzer                     (문서 파서, 웹 크롤러, 소스 라우트 파서)
    ├─ Traceability / RTM           (추적성, 커버리지 검사)
    ├─ Change 엔진                  (CR 분해, 영향도, 단계별 반영, Diff)
    └─ Renderer / Exporter          (PPTX, PDF, DOCX, XLSX, SVG, Figma, HTML)
    │
[저장소]  프로젝트 DB(JSON 문서 모델) + 파일 저장소(원문, 캡처, 산출물)
```

**권장 기술 (확정 전)**
- 프론트엔드: React + TypeScript, 다이어그램 편집은 React Flow + ELK 자동 정렬
- 백엔드: Node.js(TypeScript), 크롤러는 Playwright
- LLM: Claude API (구조화 출력으로 데이터 모델 JSON 생성)
- Export: pptxgenjs(PPTX), docx(DOCX), exceljs(XLSX), Playwright PDF 출력, Figma Plugin API 또는 Figma MCP
- 저장: 파일 기반 프로젝트 폴더(초기) → PostgreSQL(다중 사용자 단계)

## 부록 A. 단계별 인터뷰 질문 세트 (기본)
(필) = 게이트 필수 항목

**S0 공통**
- (필) 프로젝트명, 서비스명, 서비스 코드(화면 ID 접두어)
- (필) 신규 구축인가요, 운영 중인 서비스 개선인가요? → 개선이면 신규 메뉴 추가 / 기존 메뉴 수정 / 전면 개편 중 무엇인가요?
- (필) 대상 채널(PC 웹, 모바일 웹, 앱, 관리자)
- (필) 산출물 제출처와 양식(내부용 / 공공기관 제출용 / 고객사 지정 양식)
- 일정(착수, 산출물 제출 기한), 이해관계자, 검토·승인자

**S0-A 기존 서비스 분석**
- (필) 기존 정보구조도가 있나요? 없다면 ① 운영 URL로 웹 전수조사 ② 소스 저장소로 소스 전수조사 중 가능한 것을 알려 주세요.
- 로그인이 필요한 영역의 테스트 계정, 권한별 계정
- 기존 기획서·스토리보드·정책 문서, 용어 기준
- 현재 문제점, VOC, 운영 지표

**S1 기획안**
- (필) 이 프로젝트를 하는 이유(배경)와 해결할 문제
- (필) 목표와 성공 기준(KPI)
- (필) 주요 사용자 유형과 권한(회원/비회원/관리자 등)
- (필) 범위: 이번에 반드시 할 것 / 하지 않을 것
- 핵심 기능별 정책(노출 조건, 상태값, 예외)
- 외부 연계(본인인증, 결제, 기관 연계 등) 여부 — 기능·정책 수준으로만
- 제약 사항(법·규정, 웹 접근성, 개인정보, 기존 시스템)

**S2 정보구조도**
- (필) 메뉴 depth 기준, GNB 구성 원칙
- 화면 ID 규칙(조직 표준이 있는지)
- 로그인 필요 영역, 권한별 메뉴 노출 차이

**S3 다이어그램**
- (필) 처리 주체(사용자, 운영자, 시스템, 외부기관)
- 승인·반려·보완 절차, 알림 발송 시점
- 기존 플로우 자료 유무(수정 시)

**S4 스토리보드**
- (필) 화면별 입력 항목의 필수 여부·형식·글자 수(모르면 기본 규칙 제안 후 확인)
- (필) 선택 항목 옵션 목록과 기본값

**S5 프로토타입**
