# ADR-001 P0 기반 구조 결정

| 항목 | 내용 |
|---|---|
| 상태 | 채택 (P0 기준, 착수 전 결정 요청 사항 확정 시 재검토) |
| 일자 | 2026-09-25 |
| 관련 | PRD §6, §8 오픈 이슈 1·6·7 / 작업 계획 0-1 |

## 1. 제품 형태 — 파일 기반 코어 + CLI 먼저 (오픈 이슈 1)
- **결정**: 모든 기능을 TypeScript 코어 라이브러리(`src/`)로 만들고, P0~P6은 CLI(`planning`)로 검증한다. 웹 UI(P7)는 같은 코어 위에 얹는다.
- **이유**: 데이터 모델과 추적성이 모든 단계의 기반이다. UI보다 엔진을 먼저 검증해야 변경 비용이 작다. 파일 기반이라 Git으로 산출물 이력도 함께 관리된다.
- **영향**: 다중 사용자·권한(F-PRJ-06)은 웹 단계에서 DB 저장소로 옮길 때 다룬다. 저장소 계층(`src/project/store.ts`)만 바꾸면 된다.

## 2. 데이터 모델 — zod 스키마가 원본
- `src/model/schema.ts`의 zod 스키마 하나에서 타입, 입력 검증, JSON Schema(`schemas/`, `npm run gen:schema`)를 모두 만든다.
- 프로젝트 폴더의 `model/*.json` 파일 하나가 스키마 하나에 대응한다(`MODEL_FILES`). 스냅샷·Diff도 이 목록을 기준으로 동작한다.
- 저장 전에 참조 무결성(`validateModel`)을 검사하고, 오류가 있으면 저장하지 않는다.

## 3. 추적 단위 — Task
- 요구사항 → **시스템별 Task** → 산출물. RTM 상태는 Task 단위로 계산하고 요구사항은 Task에서 집계한다.
- Task 상태 규칙
  | 상태 | 조건 |
  |---|---|
  | 미착수 | 연결된 산출물 없음 |
  | 설계중 | 기획안·기능·화면·플로우 중 일부 연결 |
  | 설계완료 | 연결된 모든 화면에 스토리보드 작성 (화면 없는 Task는 플로우 노드 연결) |
  | 검토완료 | 설계완료 + 사람이 확인(`planning review`) |
  | 제외 | 요구사항이 제외 처리됨(사유 필수) |
- 요구사항 상태는 소속 Task 중 가장 늦은 상태. 단, 일부라도 진행됐으면 "설계중".
- 화면 없는 Task: `noScreenReason`이 있거나, 화면 없는 시스템(예: 외부 연계 EXT) 소속.

## 4. ID 체계 (오픈 이슈 6 — 조직 표준 수령 전 기본값)
| 대상 | 형식 | 예 |
|---|---|---|
| 요구사항 | `REQ-001` 또는 RFP 원본 ID(`--id-mode ORIGINAL`) | `SFR-002` |
| Task | `{요구사항ID}-T{nn}` | `SFR-002-T03` |
| 화면 | `{system}_{d1}_{d2}_{seq}` (프로젝트별 변경 가능) | `CVL_INF_REG_010` |
| 팝업 | 화면 ID + `_P{nn}` | `ADM_INF_REV_010_P01` |
- 삭제된 요구사항은 `DELETED` 상태로 남겨 번호를 재사용하지 않는다. 폐기된 화면 ID는 `ia.retiredIds`에 남긴다.

## 5. 시스템 구분 프리셋 (오픈 이슈 7)
- `public-civil`: PUB 대국민 포털 / CVL 민원포털 / ADM 심사자·관리자 시스템
- `general`: USR 사용자 서비스 / ADM 관리자
- 외부 연계처럼 화면 없는 시스템은 `system add EXT --no-screens`로 추가한다.

## 6. 버전
- 작업 버전은 `0.1`부터 시작. `snapshot`이 현재 버전을 `history/v{버전}/`에 고정하고 다음 번호로 올린다(`--major`는 `1.0`).
- Diff는 엔티티 ID 단위(추가/삭제/변경 필드)로 비교하고, 프로젝트의 버전 번호·수정 시각은 비교하지 않는다.
